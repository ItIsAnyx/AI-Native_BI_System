# Локальный чат через Ollama

Приложение обращается к локальной Ollama через OpenAI-совместимый API.
Ollama загружает веса и выполняет генерацию; backend обрабатывает контекст и CSV.
Установка Python-пакета `ollama` не нужна. Transformers и PyTorch для этого пути не нужны.

HTTP-эндпоинты и оркестрация чатов находятся в `app/api/chat.py`, схемы запросов
и ответов — в `app/schemas/chat.py`. В `app/agent/agent.py` остаются вызовы модели,
выполнение запрошенных ею инструментов и пересказ контекста. Адреса API не изменились.

## Установка Ollama на Windows

1. Скачайте установщик с https://ollama.com/download/windows и установите Ollama.
2. Откройте новый PowerShell и выполните `ollama --version`.
3. Проверьте сервер: `Invoke-RestMethod http://127.0.0.1:11434/api/tags`.

Windows-приложение Ollama обычно запускает сервер в фоне. Если сервер не запущен,
откройте Ollama через меню «Пуск» или выполните в отдельном терминале:

```powershell
ollama serve
```

При ручном запуске оставьте этот терминал открытым. Если порт 11434 уже занят Ollama,
не запускайте второй экземпляр. Облачная учётная запись для локального GGUF не нужна.

Официальная инструкция: https://docs.ollama.com/windows

## Импорт локального GGUF

Скачайте выбранный GGUF со страницы:
https://huggingface.co/empero-ai/Qwen3.8-4B-Distill-GGUF/tree/main

Для первого запуска можно взять `Qwen3.8-4B-Q4_K_M.gguf` (около 2.8 GB весов).
Размер файла не равен общему потреблению RAM/VRAM: контекст требует дополнительной памяти.
Автор указывает необходимость свежего движка с поддержкой архитектуры Qwen3.5.

Поместите файл в `backend/models`. Рядом создайте файл `Modelfile` без расширения:

```text
FROM ./Qwen3.8-4B-Q4_K_M.gguf
PARAMETER num_ctx 8192
PARAMETER temperature 0.6
PARAMETER top_p 0.95
PARAMETER top_k 20
```

`FROM` задаёт путь к GGUF относительно Modelfile. `num_ctx` задаёт окно в токенах;
оно влияет на потребление памяти. Остальные параметры задают настройки генерации.
Шаблон чата у выбранной модели встроен в GGUF; вручную писать TEMPLATE сначала не нужно.

Из папки проекта выполните:

```powershell
Set-Location D:\GitWorks\AI-Native_BI_System\backend\models
ollama create qwen38-local -f .\Modelfile
ollama list
ollama run qwen38-local
```

`qwen38-local` — выбранное вами имя модели в Ollama. В списке оно может отображаться
как `qwen38-local:latest`; это имя с тегом по умолчанию. Спросите модель что-нибудь.
Для выхода из интерактивного диалога используйте `/bye`.

Ollama импортирует модель в своё хранилище, а не просматривает backend/models
перед каждым запросом. Папка проекта хранит исходные файлы; нужно учитывать место
и для хранилища Ollama. Для другой модели повторите импорт под другим именем.

Официальная инструкция импорта: https://docs.ollama.com/import
Параметры Modelfile: https://docs.ollama.com/modelfile

## Проверка API отдельно от приложения

В PowerShell:

```powershell
$body = @{
    model = 'qwen38-local'
    messages = @(@{ role = 'user'; content = 'Reply with a short greeting.' })
    stream = $false
} | ConvertTo-Json -Depth 10

$result = Invoke-RestMethod -Method Post `
    -Uri 'http://127.0.0.1:11434/v1/chat/completions' `
    -ContentType 'application/json; charset=utf-8' `
    -Body $body

$result.choices[0].message.content
```

Первый запрос может быть медленным из-за загрузки весов. `ollama ps` показывает
загруженные модели. `ollama stop qwen38-local` выгружает модель; сервер продолжает работать.

Выбранная модель обучена рассуждать и может выдавать блоки `<think>`. Проверьте,
отделяет ли установленная версия Ollama рассуждения от content. В приложении пока
нет дополнительного удаления таких блоков; оно возвращает message.content как есть.

Совместимость API: https://docs.ollama.com/api/openai-compatibility

## Подключение backend

Из папки backend:

```powershell
Set-Location D:\GitWorks\AI-Native_BI_System\backend
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

Если `.env` ещё нет, скопируйте `.env.example` в `.env`. Существующий файл не затирайте:
обновите только нужные настройки. Укажите:

```dotenv
OLLAMA_BASE_URL=http://127.0.0.1:11434/v1
MODEL_NAME=qwen38-local
REQUEST_TIMEOUT_SECONDS=300
MAX_REQUEST_LENGTH=8000
MAX_CONTEXT_LENGTH=12000
TOKENIZER_PATH=models/tokenizer
MAX_CONTEXT_TOKENS=40960
MAX_RESPONSE_TOKENS=4096
MAX_CONTINUATIONS=2
MAX_FILE_SIZE_MB=10
MAX_FILE_ROWS=100000
STORAGE_DIR=storage
```

Остальные настройки БД и авторизации возьмите из backend/.env.example и заполните.
SECRET_KEY должен быть Base64-представлением случайного секрета минимум из 32 байт;
заглушка secret не подходит. PostgreSQL должен быть доступен при запуске приложения.
MODEL_NAME — имя из `ollama list`, а не путь к файлу и не имя репозитория Hugging Face.
Старые MODEL_PATH и MAX_NEW_TOKENS больше не используются.

MAX_CONTEXT_LENGTH по-прежнему запускает пересказ истории по числу символов.
Перед каждым обращением к модели дополнительно считаются токены через локальный
токенизатор с шаблоном чата и описаниями инструментов. MAX_CONTEXT_TOKENS задаёт
полное окно и должен соответствовать num_ctx в Ollama; MAX_RESPONSE_TOKENS
резервируется для ответа. Вход должен помещаться в разницу этих двух значений.

В TOKENIZER_PATH укажите каталог токенизатора именно используемой модели:
tokenizer.json, tokenizer_config.json и chat_template.jinja, если шаблон хранится
отдельно. Для иных форматов токенизатора нужны его собственные файлы из исходной
модели. Шаблон должен соответствовать шаблону, используемому Ollama. Один
tokenizer.json без описания шаблона не позволяет посчитать весь чат правильно.
Относительный путь считается от backend. Токенизатор читается только локально;
при работе API файлы не скачиваются, веса через Transformers не загружаются.
Если каталог отсутствует или шаблон не подходит, API вернёт понятную ошибку 503.
Для текущего GGUF файлы токенизатора взяты из исходной модели
https://huggingface.co/empero-ai/Qwen3.8-4B/tree/c83cb7aa2999d2f35c43e9ae0634a30eb8985a1e
и находятся локально в backend/models/tokenizer. Как и веса, они не входят в Git;
на другом компьютере эти файлы нужно положить в настроенный каталог.

Если результат инструмента переполняет окно, он заменяется сообщением об ошибке,
остальные инструменты останавливаются. Агент пробует пересказ и ответ без новых
инструментов; если пересказ не помещается или не получается, возвращается просьба
уточнить столбцы, значения или уменьшить выборку. Переполненный запрос не отправляется.

Если ответ оборван с finish_reason=length, агент пересказывает предыдущий диалог
и результаты инструментов. Последний запрос пользователя и весь начатый ответ
в пересказ не включаются и передаются целиком. Начатый ответ передаётся последним
assistant-сообщением для продолжения с его конца; инструменты при этом отключены.
Продолжения дописываются к ответу. MAX_CONTINUATIONS ограничивает число попыток;
если завершить ответ не удалось, частичный текст возвращается с явным предупреждением.

Запустите приложение:

```powershell
.\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8080
```

Ollama должна продолжать работать в фоне. Backend сам её не запускает и веса не скачивает.
При смене MODEL_NAME или других настроек перезапустите backend.

## Проверка приложения

Откройте http://127.0.0.1:8080/docs и выберите POST /agent/response.
Сначала зарегистрируйтесь или войдите через POST /api/auth/register или /api/auth/login
в том же браузере: эндпоинты чатов, источников и артефактов требуют access_token cookie.
BACKEND_KEY для них не используется. Затем нажмите Try it out и в payload вставьте:

```json
{
  "message": "Привет! Ответь одним предложением."
}
```

Поле file необязательное. Для вопроса о CSV выберите файл и измените message.
Первый запрос без chat_id создаёт чат. Ответ содержит chat_id, message_id, message,
context, sources и charts. В следующий запрос передайте chat_id из ответа и новый текст:

```json
{
  "chat_id": "UUID из предыдущего ответа",
  "message": "Покажи самые частые значения"
}
```

Контекст берётся из БД; присланный клиентом context больше не используется. Полная
история дополняется парой сообщений, active_context заменяется после ответа и может
быть пересказан. Технические tool-сообщения и base64 изображений в историю не попадают.
Новые сообщения, источники и артефакты сохраняются вместе после успешной генерации.
Если обработка прервана, принятый CSV остаётся на диске и регистрируется в Sources;
в историю и контекст добавляется запрос и сообщение о сохранённом источнике с его ID.
Незарегистрированные PNG удаляются. Чат, созданный первым
неуспешным запросом, может остаться пустым. Параллельное устаревшее сохранение получает
409 вместо перезаписи чужого результата; перед повтором нужно заново загрузить чат.

CSV читается в tools/dataset.py: автоматически выбирается запятая, точка с запятой
или табуляция, убираются пробелы. Сначала значения читаются строками. Ключи
распознаются по названиям id/uuid/guid/код/артикул/идентификатор или ведущим нулям
и сохраняются строками. Остальные полностью числовые столбцы преобразуются в числа.
Это эвристика: неоднозначные ключи отмечаются в warnings, автоматической очистки нет.

В DataFrame добавляется технический _row_id от 1 до числа строк. Если такое имя
уже занято, добавляется ещё один начальный символ подчёркивания. ID стабилен при
повторном чтении того же файла и уникален только в рамках источника. Исходный CSV
не изменяется; _row_id не заменяет бизнес-ключ для связи нескольких таблиц.

Инструмент статистики возвращает warnings, key_columns и technical_id_column.
Повторяющиеся и пустые заголовки получают уникальные имена с предупреждением.
При разном числе полей недостающие значения отмечаются пропусками, дополнительные
сохраняются в _extra_column_N; warnings содержит число и примеры таких строк.
CSV сохраняется в storage/sources/<chat_id>/<source_id>.csv. При загрузке к сообщению
пользователя добавляется ID и имя датасета. Оригинальное имя не используется как путь.
Статистику и пять примеров строк модель получает по необходимости через
read_dataset_and_gain_statistics; DataFrame подставляет приложение.
Результат инструмента остаётся в рабочем контексте текущего вызова модели,
а не дописывается к системному промпту или возвращаемому контексту целиком.
Повторно прикладывать файл не нужно. Активный источник хранится в чате; новый файл
становится активным. Для выбора прежнего источника передайте source_id вместе с chat_id.
Модель видит краткий список источников и может вызвать list_sources, затем передать
source_id любому инструменту датасета. CSV читается по необходимости; DataFrame
кэшируется только в пределах одного вызова call_llm. Пока поддерживается один файл
в одном запросе и только CSV, без внешних подключений БД.
Если контекст длинный, промежуточные сообщения заменяются одним пересказом.
Первое системное сообщение и последний запрос пользователя сохраняются.

GET /api/health проверяет только приложение; доступность модели проверяет реальный запрос.

## Чаты, источники и графики

| Метод и путь | Назначение |
|---|---|
| POST /agent/chats | Создать пустой чат, вернуть chat_id |
| GET /agent/chats | Получить свои чаты |
| GET /agent/chats/{chat_id}/history | Получить полный chat_history |
| GET /agent/chats/{chat_id}/context | Получить active_context |
| GET /agent/chats/{chat_id}/sources | Получить источники чата без внутренних путей |
| GET /agent/sources/{source_id}/file | Скачать свой CSV |
| GET /agent/artifacts/{artifact_id} | Получить свой PNG |

PNG сохраняются в storage/artifacts/<chat_id>/<artifact_id>.png. Каждый элемент charts
содержит id, url, source_id и прежние метаданные графика, но больше не image_base64.
Артефакт связан с message_id ответа; charts также сохранены в записи сообщения
chat_history. Frontend отображает изображение по url с cookie авторизации. Внешнюю
ссылку для анонимного доступа приложение не создаёт.

Таблицы chat_history, sources и artifacts создаются через create_all в lifespan.
Существующая таблица users не пересоздаётся, старые данные не удаляются. create_all
не заменяет миграции для последующих изменений уже существующих таблиц.

Текущий frontend/src/api/endpoints/workspaceApi.js остаётся демонстрационной заглушкой.
Его подключение к HTTP нужно сделать отдельно: создать или получить server chat_id,
посылать его с message, принимать charts[].url и загружать историю при открытии чата.
Старые stateless-скрипты тестов тоже требуют входа и передачи chat_id вместо context;
их сохранение image_base64 нужно заменить загрузкой charts[].url с той же сессией.

## Хранение в Docker

В docker-compose.yaml добавлен backend с volume agent-data в /app/storage. Метаданные
и переписка находятся в PostgreSQL, исходные CSV и PNG — в agent-data. Оба volume
нужны для восстановления. Обычный перезапуск и пересоздание контейнера сохраняют их;
docker compose down -v удалит volumes вместе с данными.

Перед запуском заполните корневой .env и backend/.env согласованными настройками
PostgreSQL. Из корня проекта: docker compose up -d --build. Backend доступен на 8080,
БД создаётся до старта приложения. В существующем pg-data изменение POSTGRES_DB само
по себе не создаёт новую БД. Ollama работает на хосте; её адрес внутри контейнера —
http://host.docker.internal:11434/v1. Ollama должна принимать соединения из Docker.
Для локального запуска STORAGE_DIR=storage считается относительно папки backend.

## Ошибки

- 401: отсутствует или истекла access_token cookie; выполните вход/refresh.
- 404: чат, источник или артефакт не найден либо принадлежит другому пользователю.
- 409 с code=agent_busy: агент ещё работает в этом чате; дождитесь ответа.
  Защита от повторного запуска хранится в памяти одного процесса backend.
  Повтор без chat_id блокируется, пока выполняется первый запрос без chat_id этого пользователя.
- 409 без code=agent_busy: чат изменён параллельным запросом; загрузите актуальную историю перед повтором.
- 422: неверный payload или пустое сообщение.
- 503 с Cannot connect: Ollama не запущена или указан неверный OLLAMA_BASE_URL.
- 503 с Model not found: MODEL_NAME не совпадает с именем импортированной модели.
- 504: превышен REQUEST_TIMEOUT_SECONDS; проверьте модель отдельно и при необходимости увеличьте таймаут.
- 502: Ollama отклонила запрос или вернула пустой ответ; проверьте её логи и прямой запрос.
- Ошибка архитектуры при импорте/загрузке: обновите Ollama и проверьте поддержку модели.
- Нехватка памяти: уменьшите num_ctx в Modelfile и повторите ollama create либо используйте меньшую модель.

Логи Ollama на Windows находятся в `%LOCALAPPDATA%\Ollama`, в частности server.log.
Установка зависимостей backend не устанавливает саму Ollama.

## Смена модели

Импортируйте другой GGUF под новым именем и проверьте `ollama run`. В конфиге измените
MODEL_NAME, TOKENIZER_PATH на каталог токенизатора этой модели и MAX_CONTEXT_TOKENS
на её num_ctx, затем перезапустите backend. Каталог backend/models доступен в Docker
как /app/models только для чтения. Выпадающий список моделей и загрузка через UI пока не реализованы.
